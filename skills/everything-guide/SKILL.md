# Karpathy Guidelines

> "模型会代你做错误的假设，然后不假思索地执行。它们不管理自身的困惑，不寻求阐明，不提出矛盾，不展示权衡，在应该提出异议时也不反驳。"
>
> "他们真的很喜欢把代码和 API 搞复杂，堆砌抽象概念，不清理死代码……明明 100 行能搞定的事情，非要实现成 1000 行的分析架构。"
>
> "他们有时仍然会列出或删除自己理解不足的代码和注释，即使这些内容与任务本身相关。"

## 解决方案

四个原则，集中在一个文件中，直接解决这些问题：

| 原则 | 解决什么问题 |
|---|---|
| 编码前思考 | 错误假设、隐藏困惑、不展示权衡 |
| 简单优先 | 过度工程、过度抽象、过度概括 |
| 精准修改 | 无关编辑、接触不该碰的代码 |
| 目标驱动执行 | 测试先行、可验证的成功标准 |

## 四个原则详解

### 1. 编码前思考

**不要脑补假设。不要隐藏困惑。要展示权衡。**

LLM 经常默默地选定一种解释然后执行。这个原则强制显式推理：

- 明确说出假设 —— 不确定就问，不要猜
- 列出多种解释 —— 有歧义时不要默默二选一
- 该反驳就反驳 —— 有更简单的方法就直接说出来
- 困惑时喊停 —— 指出不清楚的点并要求澄清
- **陈述事实要有依据** —— 任何以事实语气输出的内容（存在/不存在、路径/位置、行为/结果、版本/API、清单）都必须有已验证来源（读过代码、跑过工具、官方文档）。凭记忆的明标为"我记得 / 待确认"，或直接说"没查到"；尤其警惕"XX 不存在"这种否定断言——默认说"我没找到"

### 2. 简洁优先

**用最少的代码解决问题。不要过度预测未来。**

对抗过度工程的倾向：

- 不要加没被要求的功能
- 不要为三个相似的用法就抽象出一层
- 不要加没被要求的"灵活性"或"可配置性"
- 不要为不可能发生的场景做防御性错误处理
- 如果 200 行代码可以写成 50 行，就重写

检验标准：资深工程师会觉得这过于复杂吗？如果是，简化。

### 3. 精准修改

**只碰必须碰的。只清理自己造成的破坏。**

编辑现有代码时：

- 不要顺手"改进"无关的代码、注释或格式
- 不要重做没坏的东西
- 遵循现有风格，即使你更倾向别的写法
- 如果注意到无关的死代码，提一下就好——不要擅自删除

当你的改动让某些代码变成孤儿时：

- 删除因为你这次改动而变得无用的 import / 变量 / 函数
- 不要删除本来就存在的死代码，除非被明确要求

检验标准：每一行改动都应该能直接追溯到用户的修改请求。

### 4. 目标驱动执行

**定义成功标准。循环验证直至达成。**

将指令式任务转化为可验证的目标：

| 不要这样做... | 转化为... |
|---|---|
| "添加验证" | "为无效输入编写测试，然后让它们通过" |
| "修复这个 bug" | "编写能**重现** bug 的测试，然后修复至测试通过" |
| "重构 X" | "确保重构前后测试都通过" |

对于多步任务，先列出一份简短的计划：

```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```

**清晰强的成功标准**让 LLM 能够独立循环执行直到达成；弱标准（"让它跑起来就行"）则会逼模型不断回头找你确认。
