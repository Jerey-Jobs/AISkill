### 写文档的规范
- 当你在写文档的时候，最好先考虑下文档中需要有图片不，如果在写一个飞书文档，可以增加一些图片，让文档更好理解。图片可以用曲线/折线图/条形图等生成
- 如果一定要写md,那无法用图片，可以咨询下是否要生成html这样会更好
- 文档顶部需要有整个文档的总结性话术,结构化思维。金字塔思维。
- 写文档需要注意标题等级递进问题
- 写文档结论先行,先用一句高亮的话描述好下方要写的内容以及总结结论
- 写文档注意记得插图以及颜色区分,重点问题要标蓝色或者红色,但不要太多,只标注最重要的部分进行高亮
- 写文件过程中,文字不要太多,如果文字表达多的部分,可以用表格、流程图进行表述档时规范
- 要注意前后的逻辑,另外不要重复论证
- 语言尽量简洁,且有足够的支撑,让人无法反驳
- 能用流程图的地方,可以优先选择图来表示,画图不希望连接线交叉,分层级绘制,结构清晰明了。不要有太多曲线,尽量使用直线。
- 画图的时候,分层设计明确。但最多不要超过 5 层(架构全景图可放宽到 7-9 层,但每层内再分组)。

### 工程类文档特别要点(实战教训)

写"怎么做 X"的技术文档时,容易犯的错和修正:

- **区分"工作日志"和"指南"**。"这次我是怎么做的"属于工作日志,"以后别人遇到类似问题该怎么做"才是指南。写指南时,把本次具体的场景/数据/bug 压缩到"案例节选"一小节就够,主体要通用化(第三人称"遇到 X 时怎么办",而不是"本次我是怎么排查 X 的")。用户如果说"写得太和本次相关了",就是在提醒你跑偏了。

- **概念先行,工具后置**。不要上来就讲"怎么抓日志、怎么跑脚本"。先讲三件事:1) 这个问题是什么(定义 + 现象),2) 怎么判断自己遇到了(识别信号),3) 为什么难(痛点)。概念讲透,读者才知道自己的问题是不是属于这类,后面的步骤才有意义。

- **明确 AI 分工**。现在的工程流程里,日志解析、脚本生成、代码 patch 都可以交给 AI。独立一章讲"哪些步骤让 AI 做 / 人做什么决定",并给出**每步的提示词示例**。写成"人:复现/抓日志/做决定 | AI:切日志/画图/写 patch"这种对照清单,读者照着就能用。

- **本地路径是毒**。`/home/mi/...`、`~/work/...` 这种路径别人打不开,出现在文档里等于白写。替代方案(按优先级):
  1. 可以贴全文的(patch、脚本、配置)**直接贴文档正文**或附录代码块里,读者 copy 就能用
  2. 大二进制(截图、HTML 报告)用飞书/Wiki 的**附件上传**,不要给本地绝对路径
  3. 实在要提路径,用**相对路径 + 查找方法**(如"`~/.pub-cache/git/xxx-<hash>/...`,`<hash>` 通过 `grep ... package_config.json` 自查")

- **写完自检清单**:
  - [ ] 读者不在我的机器上,他能照着做吗?
  - [ ] 标题的"一二三"是"对未来读者的指引",不是"我这次的时间顺序"?
  - [ ] 每个本次才有的具体值(id、timestamp、commit hash)都压缩到案例里了?
  - [ ] 代码和脚本是贴出来的,不是指向本地文件的?

### 飞书 MCP 上传本地图片踩过的坑

用 `feishu-mcp-pro` 插入本地图片时,**两个条件必须同时满足**才能真上传:

#### 条件 1:URL 用四斜线 `file:////`

- ❌ `<image url="/home/mi/x.png"/>` — 无 scheme,`Failed to parse URL`
- ❌ `<image url="file:///home/mi/x.png"/>` — MCP 会吞一个 `/`,变成相对路径 `home/mi/...`,`ENOENT`
- ✅ `<image url="file:////home/mi/x.png"/>` — 四斜线,吞一个后剩下 `/home/mi/...`

#### 条件 2:必须用 `doc_append`,不能用 `doc_update`

这是更隐蔽的坑。实测:

| 工具 | 是否触发自动上传 |
|---|---|
| `doc_append` | ✅ 会真上传,返回 `images_processed: N`,image block 有有效 token |
| `doc_update insert-before / insert-after / replace` | ❌ 只插入 block 但**不上传图片**,token 永远是空字符串 |

返回都是 `success: true, blocks_added: 1`,**不看 `images_processed` 字段无法区分**。

#### 实战做法

想把图放在文档中间某位置(比如 §1 开头)时:
1. 用 `doc_append` 把图追加到**文档末尾**(得到有 token 的真图)
2. 用 `doc_update insert-before` 在目标位置插入**文字引用**(比如"图见文末附录")
3. 文末追加一节"附录:XX图",和图放一起

不要指望 `doc_update` 能把图塞到任意位置,做不到。

#### 识别和修复空 token 图

- `doc_list_blocks` 找 `block_type == 27` 且 `image.token == ""` 的 block
- `doc_delete_blocks_by_ids` 删掉
- 走上面"实战做法"重新插

### 飞书 MCP 表格单元格里不能放格式标签

markdown 表格单元格里写 `**bold**` / `<text color="...">` / `<callout>` 都会**破坏 table 解析**，整行被原样输出成字面 `| ... |` 字符串（连表格线都看得到）。

✅ 正确做法：
- 单元格内只放**纯文本 / 数字 / emoji**（✅、🔴、→ 等可以）
- 高亮 / 加粗 / 颜色放到表格的**前置段落**或**后置 callout**

```markdown
<text color="red">**4 月降至 27 亿，达标**</text>

| 时间 | 数值 |
|---|---|
| 4 月 | 27 亿 ✅ |

<callout color="green">**最终达标**：低于友商 33.3 亿。</callout>
```

### 飞书 MCP 不支持 heading 颜色属性

❌ `## 结论 {color="blue"}` → `doc_write` 直接 `Request failed with status code 400`。

文档说 heading attribute `{color="..." align="..."}` 支持，实测**不可用**。避免使用，结构靠 H2/H3 层级 + callout 区分。

### 飞书 MCP 写文档自检清单

`doc_write` / `doc_append` 大段 markdown 之前过一遍：

- [ ] 表格单元格是不是纯文本/数字/emoji？没有 `**` / `<text>` / `<callout>`？
- [ ] 标题没有 `{color="..."}` / `{align="..."}` 属性？
- [ ] 图片是 `file:////` 四斜线 + 用 `doc_append`（不是 `doc_update`）？
- [ ] 高亮放在表格 **外** 的段落或 callout？
- [ ] 写完用 `doc_read` 看一下，正文里有 `| 4 月 | 27 亿 |` 这种字面字符串就是表格炸了

### 画图工具 · drawio MCP

画**架构图 / 流程图 / 分层图 / 时序图 / 状态机**时,用 drawio MCP
(仓库:https://github.com/DayuanJiang/next-ai-draw-io)。

**检查是否已安装**:

```bash
claude mcp list | grep drawio
```

看到 `drawio: ... - ✓ Connected` 就是装好了,跳过安装步骤直接用。

**未装则安装**(仅新机器首次):

```bash
claude mcp add --scope user drawio -- npx -y @next-ai-drawio/mcp-server@latest
```

装完 `/exit` 重开 Claude Code 生效。

**画图时注意**(踩过的坑):

- 画布保持 **800×600** 单页,不要超
- 连线用正交直线(`orthogonalEdgeStyle`),不允许交叉
- 修改已有元素前**必须先调 `get_diagram` 再调 `edit_diagram`**(协议强制)
- 注意检查画图不要有遮挡，可以适当动态调整文字。
